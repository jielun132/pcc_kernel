# PCC 0.1.7 操作步骤

准备三个独立环境：`prod` 为采集源，`old` 和 `new` 为升级前后的临时集群。演示造数使用独立的模拟生产集群。操作机需要 MySQL 8 客户端；PCC Linux 安装包自带 Python 和应用依赖。

**从 0.1.6 升级时**，先退出旧菜单。采集计划进行中可按一次 Ctrl+C，等回到菜单后输入 `0`。把新包和同名校验文件放在原安装目录的上一级，在该目录执行以下命令。将文件更新到原目录，保留现场配置和任务的原有路径；若原目录改过名，替换下面两处 `pcc-core-0.1.6-linux-x86_64`：

```bash
sha256sum -c pcc-core-0.1.7-linux-x86_64.tar.gz.sha256
tar -xzf pcc-core-0.1.7-linux-x86_64.tar.gz \
  --directory=pcc-core-0.1.6-linux-x86_64 --strip-components=1 \
  --exclude='pcc-core-0.1.7-linux-x86_64/pcc.json'
cd pcc-core-0.1.6-linux-x86_64
./pcc --version
./pcc
```

已生成过报告时，先选 `7` 离线重算上次采集。核对终端的原始计划统计、“规则 v6”和“待复核原因”三行，再打开新打印的 `report.html`。

1. 点击报告上方的“待复核”。搜索 `SQL-0293`，查看 D01 的原因、两端的 `TableDual rows:0` 和“复核方法”。
2. 点击顶部“全部样例”清除待复核筛选，在目录中搜索 `SQL-0382`。展开“运行时提示”，查看 D05 和实际扫描量的核对方法。
3. 展开“选择规则与阈值”，查看 4 张默认必审卡和 9 张运行时提示卡。需要扩大范围时选“推荐规则＋复核运行代价”，再点“按所选规则重新判断”。恢复默认时选“恢复推荐”并重新判断。导出判断 CSV 可同时保存必审原因和运行时提示。
4. 需要复核 D01 时，在两端有相同代表性数据的隔离库使用报告中的绑定参数，分别运行普通 `EXPLAIN`。记录子查询的值、外层出现的范围和算子。需要核对只读查询的运行代价时，再在隔离库查看实际行数、循环、内存和耗时。

要重新连接原有两端采集计划，选 `6` 检查账号，再选 `4` 继续原任务。首次安装从下面第 1 步开始。

### 设置采集并发

在安装目录的 `pcc.json` 中，把 `workflow.concurrency` 设为 `8`。新模板默认是 8，原配置中明确填写的 2 会继续生效。允许 1 至 16 的整数，按每端计算。填 8 时，预热和正式采集从第一批起可同时处理 old 8 份、new 8 份。进度行显示阶段、两端在途数和上限。

正在采集时，按一次 Ctrl+C，等菜单显示进度已保存，输入 `0` 退出。改好数字后重新启动并选 `4`，从上次任务继续。已保存的有效计划和统计复查记录会复用。

## 用已有固定材料复测 413 条

已有的 0.1.6 固定材料可继续使用，不需要更改材料版本或内容。

1. 已取得固定材料时，在安装目录解压 `pcc-demo-reference-0.1.6.tar.gz`。命令为 `tar -xzf pcc-demo-reference-0.1.6.tar.gz`。
2. 运行 `./pcc`，选择 `3`，输入 `pcc-demo-reference-0.1.6/bundle`。
3. 第一次选 `1`，核对两个隔离目标和库名，输入 `IMPORT`。等待“普通 EXPLAIN 预热”和“正式采集”两轮完成。两端都已导入后，主菜单 `4` 可重采。中断后仍选 `4` 继续。
4. 记下终端的三行计数。选择 `7`，核对离线重算的三行计数，再打开新报告。

从正式安装包开始演示时，可按后面的第 3、4 步自行生成 413 条案例并取源统计。已有的固定材料包含 SQL、参数、DDL 和源统计。该模式可以跳过演示源端造数与 ANALYZE。现场配置中的 `expected_version` 仍填写各节点实际返回的 Release Version。

## 1. 解压并配置

把 0.1.7 安装包和同名 `.sha256` 文件放到操作机同一目录，执行：

```bash
sha256sum -c pcc-core-0.1.7-linux-x86_64.tar.gz.sha256
tar -xzf pcc-core-0.1.7-linux-x86_64.tar.gz
cd pcc-core-0.1.7-linux-x86_64
vi pcc.json
```

在 `profiles.prod`、`profiles.old`、`profiles.new` 中填写：

| 字段 | 填写内容 |
|---|---|
| `host`、`port`、`user` | 对应 TiDB 的 SQL 地址、端口和用户名 |
| `status_url` | 对应 TiDB 节点的 Status 地址，如 `http://主机:10080` |
| `expected_version` | `SELECT tidb_version();` 中的精确 Release Version，例如 `v6.5.12`、`v7.1.9-0.3` |
| `password_env` | 保留变量名，不填写密码；相同密码共用 `PCC_DB_PASSWORD`，不同密码分别填写不同变量名 |
| `role` | 源端保持 `source`；old/new 保持 `test` |

在 `workflow.mysql_client` 填写 MySQL 客户端路径。`mysql` 已在 PATH 中时无需修改。其他默认值可保持不变。

模板使用无 TLS 连接。启用 TLS 的集群应在对应 profile 增加 `tls` 和 `status_tls` 的 `ca` 路径；双向认证时同时填写 `cert`、`key` 路径。

## 2. 启动菜单

```bash
./pcc
```

输入 `6`，按提示输入数据库密码，逐行核对 prod、old、new 的登录结果。相同密码变量在本次菜单会话共用。若提示 1045 且密码是刚刚手输的，再选 `6` 重新输入。

## 3. 生成完整演示案例

在菜单输入 `1`。工具生成一个新目录：

- `setup.sql`：建表和造数，创建三个新演示库。
- `queries.jsonl`：全部 413 条待比较 SQL 及 Prepared 参数。
- `CASES.md`、`case-index.json`：案例编号、类别和预期守卫结果。

保留 PCC 菜单窗口，另开一个终端，复制菜单显示的 MySQL 登录命令。登录模拟生产集群后，复制菜单显示的这一行执行：

```sql
source /菜单显示的完整路径/setup.sql;
```

看到 `PCC demo setup completed` 后退出 MySQL：

```sql
exit
```

同一个 `setup.sql` 只执行一次。再次演示时重新选择菜单 `1`，使用新生成的库名和文件。

## 4. 比较 413 条 SQL

回到 PCC 菜单：

1. 输入 `3`。
2. SQL 文件路径直接回车，使用刚生成的 `queries.jsonl`。
3. 导出完成后直接回车，选择“导入并比较”。若想先把 old、new 都导好，稍后再比，在这一步输入 `3`。
4. 核对 old/new 地址、实际版本和待创建库，输入 `IMPORT`。
5. 选择“只导入两端”时，看到“两端已导入”即可退出；准备好后再启动 `./pcc`，选主菜单 `4`。PCC 会核对两端材料并开始采集。
6. 观察执行计划进度。413 条 SQL 对应 826 份双端任务。old、new 分别显示已处理数。遇到统计加载告警或 `pseudo` 时，相应端先保存告警并继续其他案例，稍后只复查该端。进度行显示待复查数、当前案例、正在执行的步骤、本次耗时和 PCC 峰值内存。
7. 记下 `report.html` 路径。需要降低对测试机的并发压力时，按一次 Ctrl+C，等菜单提示已保存后退出，把 `workflow.concurrency` 改为 `1`，重新启动并选 `4` 续跑。之前的统计复查记录和已完成的有效计划都会复用。

两个临时集群都必须不存在本次演示库。目标表中没有业务数据是正常的，不要在 old/new 执行 `setup.sql` 或 `ANALYZE`。

## 5. 查看报告

把菜单给出的 `report.html` 下载到电脑，用浏览器打开。

1. 核对总数为 **413**。
2. 搜索 `SQL-0001` 等案例编号，对照 `CASES.md` 查看 SQL 和双端计划。要追溯慢案例，展开对应端的“上下文、原始计划与警告”，查看 `attempts` 中每次返回的告警和 `explain_ms`（从客户端发出 EXPLAIN 到收完结果的毫秒数）。
3. 查看“存在差异”，勾选规则后点击“按所选规则重新判断”。
4. 分别检查变优、变差、基本等价、待复核的依据。
5. 查看“无法比对”，检查错误或缺失材料。

`SQL-0403` 至 `SQL-0413` 是 11 条预期拦截案例，应保留未运行状态。其余无法比对项需要逐条查看原因。不同版本和统计信息下，一致、差异数量可以不同；不要把计划变化直接当成性能变差。

## 6. 按时间采集实际 SQL

需要检查已有业务 SQL 时，使用菜单 `2`：

1. 输入开始时间，例如 `2026-11-03 09:00:00`。
2. 输入结束时间，例如 `2026-11-03 11:00:00`。
3. 输入库名，多个库用逗号分隔。
4. 导出完成后核对显示的入选指纹数、SQL 样例数和双端任务数。按提示导入 old/new 临时环境，输入一次 `IMPORT`。

无时区的输入按源端配置的 `timezone` 解释。默认五个维度各取 Top 20 后合并去重，时间范围须有源端仍保留的 Statement Summary 数据。

经常使用的库名、时间、Top N 和输出目录可以预先填写在 `workflow.schemas`、`begin`、`end`、`top_n`、`out_dir`，下次按回车使用。配置中的相对输出路径以 `pcc.json` 所在目录为基准。

## 7. 继续任务或重新查看

| 需要做什么 | 操作 |
|---|---|
| 重启工具后继续已导出的任务 | `./pcc` → `4` |
| 已人工完成导入 | 继续任务时选择 `2`，直接比较 |
| 找报告路径 | 菜单 `5` |
| 完全离线重算最近报告 | 菜单 `7` |
| 重新生成一套演示库 | 菜单 `1` |
| 退出菜单 | `0` |

导入失败时先核验提示的目标，不要直接重跑导入。程序会保留已完成的一端；部分建好的库需要人工处理，或换用新的演示库。导出中断尚未生成完整 bundle 时，重新选择 `2` 或 `3` 新建任务。

比较完成后显示的 PCC 返回码：`0` 为完整比较且一致，`1` 为完整比较且有差异，`3` 为部分未完成；`3` 时打开报告查看原因。菜单本身退出成功不代表所有 SQL 均已完成比较。
